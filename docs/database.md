# MySQL、PostgreSQL、SQLite 简单对比

在开发里，MySQL、PostgreSQL（常简称 PSQL）、SQLite 是最常用的三款关系型数据库，三者定位差异巨大，选库的核心，就是看懂它们的架构、并发能力与适用场景。

SQLite 属于嵌入式数据库，没有独立服务进程，整个数据库仅仅是磁盘上的一个文件。使用它不需要单独部署后台服务，没有账号密码、没有访问端口，程序依靠驱动直接读写文件，天然上手简单，复制文件就等于备份数据库。也正因如此，它非常适合移动端 App、桌面软件、本地缓存以及单元测试。

但 SQLite 的并发特性有明显局限：它支持并发读取，开启 WAL（先写日志，再改数据页） 模式之后，读操作还可以和写操作同时进行；可是无论任何模式，同一时刻只允许一个写入事务，写操作是串行排队的。一旦大量请求同时写入，就容易出现排队、超时，因此不适合作为多服务共享的数据库。

MySQL 和 PostgreSQL 则是典型的客户端 / 服务端数据库，需要单独安装并启动后台进程，依靠 TCP 端口通信，MySQL 默认端口 3306，PostgreSQL 默认端口 5432。访问时需要配置账号、权限，线上业务一般还要搭配连接池复用连接，降低频繁创建连接带来的开销。

二者都完整支持 ACID（事务的四个特性）、MVCC（多并发版本控制） 和行锁，能够很好支撑并发写入，不同行的数据可以同时修改，不容易出现单点写阻塞。相对来说，MySQL 的生态更加普及，资料、运维工具成熟，是国内大量普通 Web 业务的首选，适合读多写少的线上业务。PostgreSQL 对 SQL 标准的兼容性最好，高级能力丰富，支持 JSONB、自定义类型、数组、地理信息、复杂查询，在数据分析、业务逻辑复杂、对数据一致性要求高的项目里更占优势。

高并发，指短时间内有海量请求涌向数据库。高并发写场景，是 SQLite 的短板，却是 MySQL 和 PostgreSQL 的主场。并发不等于并行：并发是任务快速交替执行，并行是多核同时执行；日常开发所说的高并发，重点考验数据库处理大量读写竞争的能力。

三者没有绝对的好坏，只看场景。如果只是本地存储少量数据、单程序使用，优先选择 SQLite；如果开发普通 Web 后台，想要资料多、上手容易，优先 MySQL；如果项目存在复杂查询、需要强数据一致性，或是要做数据分析，PostgreSQL 会是更好的选择。

**SQLite：文件库，零部署，读并发不错，写能力弱，适合单机本地存储**
**MySQL：流行服务端数据库，生态庞大，适合绝大多数常规线上业务**
**PostgreSQL：功能完备，贴近 SQL 标准，擅长复杂查询与高一致性场景**
